# DyCAPS 原生运行核验

日期：2026-09-20。版本：`09d226205ef86860b8c9fa7dcd78857944f8bedc`。本机 Go 1.26.2。

## 结论

原协议可以运行。未修改的命令程序完成四节点到四节点的 TCP 交接；上游十节点完整流程测试也完成，两条重构路径均恢复初始化秘密。发布的启动脚本需要修正两个角色名，完整 `go test ./...` 仍包含前次记录的格式化检查及测试端口问题。

## 可重复执行

从项目根目录运行：

```bash
python3 experiments/verification/dycaps_native.py
```

运行器编译原始 `cmd/DyCAPs`，在临时目录生成初始化参数与端口列表，然后启动四个旧成员、四个新成员和初始化客户端。四个新成员都写出 `ShareDistLatency` 记录后，结束本次创建的进程。初始化文件随临时目录移除。

随后运行上游 `TestCompleteProcess`，只通过 Go overlay 将测试中固定的端口替换为本次分配的端口，保留原来的十节点、容错三节点及协议逻辑。原测试只打印重构值，运行器额外核对两条重构路径都等于原值 `1111111111111112345`。

日志及结果目录：`experiments/results/upstream-verification/dycaps/`。

## 启动脚本问题

`cmd/DyCAPs/test_multiCommittee.sh` 使用 `currentCommitee` 和 `newCommitee`。`main.go` 实际接受 `oldCommittee` 和 `newCommittee`。原程序收到前两种名称时返回零状态，未启动委员会职责；因此脚本启动成功不能作为交接完成的依据。核验已实际调用错误角色并观察到这一行为。

本运行器使用正确的原生参数，检查后继完成记录。与上游脚本相比，另一个变化是单次编译后启动所有成员，并把参数及输出放在本次运行目录。
